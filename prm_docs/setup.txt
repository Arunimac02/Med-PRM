MULTIMODAL MEDICAL PRM - SETUP PROGRESS NOTES
===============================================

GOAL
----
Build a multimodal medical Process Reward Model (PRM), extending the
existing text-only Med-PRM codebase. Plan:
  1. Use VQA benchmarks: VQA-RAD, SLAKE, MedXpertQA-image (no text-only
     QA benchmarks needed for this).
  2. Generate chain-of-thought reasoning traces using Qwen3-VL-8B-Instruct
     plus one strong ~7B medical VLM (chose HuatuoGPT-Vision-7B-Qwen2.5VL).
  3. Collect both correct and incorrect traces in a uniform format
     (question, image, step-by-step reasoning, final answer, correctness
     label), and review the incorrect ones.

   .verify() gives false positives on images the `datasets` library has

2) Normalization into a common schema
   Script: python_mm/1_normalize_data.py
   Reads all 3 downloaded datasets and writes one unified JSON manifest:
       dataset_mm/normalized/mm_benchmark.json

   Common schema per row:
     - question_id     : unique global integer, 1..N across all sources
     - data_source      : "vqa_rad" | "slake" | "medxpertqa_mm"
     - split             : original split name (train/validation/dev/test/unmatched)
     - question          : question text
     - options           : {"A": "...", ...} for MedXpertQA (MC), {} otherwise
     - correct_answer    : answer text, or correct letter for MedXpertQA
     - answer_type       : "MC" | "CLOSED" | "OPEN"
     - images            : list of image file paths (always a list)
     - modality          : imaging modality if the source states it directly, else None
     - source_metadata   : remaining original fields, kept for traceability

   Images are referenced by path (not copied/re-encoded) -- the manifest
   points at the real image files already extracted under dataset_mm/.
   This means the manifest is NOT self-contained: deleting the raw
   per-dataset folders (vqa_rad/imgs, slake/imgs/imgs,
   medxpertqa_mm/images/images) would break the image paths.

   Result: 11,286 total rows (VQA-RAD 2248, SLAKE 7033, MedXpertQA-MM
   2005). 0 missing image files out of 12,139 total image references.
   question_id confirmed unique and sequential 1..11286.

5) Multimodal trace-generation script written
   Script: python_mm/3_generate_traces.py (multimodal equivalent of
   python/3_test_dataset_sampling.py). Not yet validated against real
   model output -- see smoke test status below.

   Design decisions:
   - Local images are attached to vllm's LLM.chat() using the
     "image_pil" content-part shorthand (pass a PIL.Image object
     directly in the message content list), not base64 data URIs.
     Confirmed by inspecting vllm.entrypoints.chat_utils
     .CustomChatCompletionContentPILImageParam in the actual installed
     vllm (0.28.0) before writing this -- it wasn't documented anywhere
     obvious.
   - MC questions (medxpertqa_mm only) already have their answer choices
     embedded in the question text by 1_normalize_data.py, so the MC
     prompt doesn't re-format an options list.
   - Both the MC prompt and the CLOSED/OPEN prompt use the same
     '## Step {number}: ' markdown step-marker convention (with the
     leading '## '), matching python/3_test_dataset_sampling.py's
     OPEN_SYSTEM_PROMPT convention exactly, since prm_process_solution's
     "ки"-tagging depends on recognizing that marker. STEP_PATTERN is
     `r"(?:## )?Step \d+:"` so it still tolerates text without the '## '
     prefix too.
   - CLOSED/OPEN final-answer phrase is '## Final Answer: {answer}'
     (not the text pipeline's '## Final Diagnosis: {Disease name}',
     since VQA-RAD/SLAKE closed/open answers are often not diagnoses --
     e.g. "yes", "MRI", "right kidney"). Prompt explicitly keeps the
     original "must output a concise and clearly defined diagnostic
     term" instruction, and adds "...or simply 'Yes' or 'No' if the
     question is a yes/no question" plus two examples covering both
     styles.
   - prm_processed_solution / orm_processed_solution: these are NOT
     produced by running an actual PRM or ORM model. They're pure text
     reformatting of the raw "solution" field (strip markdown/newlines,
     append the literal token " ки" per-step or once for the whole
     solution) -- preparing the two candidate input shapes that a later,
     not-yet-written multimodal training script will consume, exactly
     mirroring how python/2_training.py / 2_training_lora.py consume
     these same two fields today (replacing "ки" with "+"/"-" based on
     the score label). The raw "solution" field is kept in the output
     specifically so it can still be read by a human (for the "review
     the incorrect ones" step) and by the future OPEN-answer LLM-judge
     step, without needing to regenerate anything.
   - Scoring: MC = exact letter match; CLOSED = normalized
     (whitespace-collapsed, lowercased) exact text match; OPEN =
     unscored ("score": "None"), same convention as the text pipeline's
     OPEN_SOURCES.

     was sized for a much heavier 2x-A100 sharded full-dataset job and
     wasn't re-derived for this smoke test; 16GB is plenty since the
     ~8B model itself lives in GPU VRAM, not host RAM).

   Hit three environment issues running this on the actual cluster
   (compute node g084, gpu partition), all specific to PRM_mm's newer,
   unpinned vllm (0.28.0) vs. the text pipeline's pinned vllm==0.8.4 --
   none of these showed up in the original text-only pipeline:
     a) `LLM(..., device="cuda")` -- TypeError, `device` was removed
        from vllm's EngineArgs entirely in this version. Fixed by
        dropping the kwarg (GPU selection is handled separately via
        CUDA_VISIBLE_DEVICES).
     b) Compute nodes on this cluster have no internet access (only
        login nodes do). vllm/huggingface_hub tried to reach the Hub
        anyway (to check for updated config files) and failed with
        "Network is unreachable". Fixed by exporting HF_HUB_OFFLINE=1
        and TRANSFORMERS_OFFLINE=1 in the SLURM script, forcing use of
        the already-downloaded local cache.
     c) vllm 0.28's V1 engine defaults to an optional FlashInfer-
        accelerated sampler (VLLM_USE_FLASHINFER_SAMPLER=True by
        default in vllm/envs.py) which JIT-compiles a CUDA kernel on
        first use via nvcc -- not available by default in the PRM_mm
        conda env or on the compute node's PATH. Fixed by adding
        `module load CUDA/13.1.0` in the SLURM script (matches PRM_mm's
        installed torch, which is built for CUDA 13.0) so nvcc is
        available, rather than disabling FlashInfer.

      HUATUO (19658750): FAILED after 33m49s with
      `vllm.exceptions.VLLMValidationError: The decoder prompt (length
      4210) is longer than the maximum model length of 4096.`
      Root cause: `max_model_len=args.max_tokens` in the LLM(...) call
      -- this wrongly conflated the TOTAL context window (prompt text +
      image vision-tokens + generation) with `max_tokens`, which is
      meant to be only the generation budget. A real VQA-RAD prompt
      (question text + 1 image) tokenized to 4,210 tokens under
      Huatuo's own processor, before generation even started -- already
      over the 4096 cap. Smoke tests never caught this because their
      prompts were short enough to stay under it by coincidence.
      Why Huatuo hit this and Qwen (so far) hadn't: each model has its
      own vision encoder that converts the SAME image into a different
      number of tokens (patch size / resolution-handling differences).
      HuatuoGPT-Vision-7B-Qwen2.5VL is built on the Qwen2.5-VL
      architecture (dynamic-resolution vision encoder, tends toward
      more image tokens per image); Qwen3-VL-8B-Instruct's newer vision
      encoder produced fewer tokens for the same images in what's been
      processed so far. This is very likely a "when, not if" issue for
      Qwen too, given the same design flaw applies to both models and
      the dataset includes multi-image questions (up to 4 images) and
      long medxpertqa_mm vignettes not yet reached by Qwen's job.
      Decision: leave Qwen running / keep monitoring rather than cancel
      it pre-emptively, since it's making real progress. Checked both
      models' actual native max context length before deciding on a fix
      approach: Qwen3-VL supports 262,144 tokens, Huatuo/Qwen2.5-VL
      supports 128,000 -- so the model architectures are not the
      constraint at all, only the mistaken config value was.
      Rejected an unmeasured "just pad it a lot" fix (max_model_len=16384,
      picked with no real basis beyond "4x the one observed failure").
      Instead, writing python_mm/measure_prompt_lengths.py to find the
      TRUE maximum prompt length (real text + real image tokenization,
      via each model's own AutoProcessor, CPU-only, no vllm/GPU needed)
      across all 11,286 questions for both models, so max_model_len can
      be set to an exact, justified value (true max + max_tokens)
      instead of a guess.

      Measurement result (uncapped): Qwen max=9,157 tokens (question_id=
      10848, 1 image), Huatuo max=11,950 tokens (SAME question_id=10848
      -- Huatuo needs ~30% more tokens than Qwen for the identical
      image+text, confirming the two models' vision encoders tokenize
      images differently: Huatuo/Qwen2.5-VL's dynamic-resolution scheme
      tends to produce more tokens per image than Qwen3-VL's for the
      same picture). p50/p95/p99 (Qwen): 402/1586/2910. p50/p95/p99
      (Huatuo): 470/2014/3755.

   f) Considered just setting max_model_len to (measured max + max_tokens)
      per model (13,253 for Qwen, 16,046 for Huatuo) and stopping there,
      but chose instead to also fix the root cause -- a single
      unusually-high-resolution image being allowed to blow up into
      thousands of tokens -- via vllm's `mm_processor_kwargs={"max_pixels":
      N}`, which caps how large an image is allowed to be scaled up
      before it's tiled into vision-tokens, regardless of the source
      file's real resolution. Rationale: fixing the cause bounds the
      problem for every image in the dataset, not just the one specific
      question found by a finite measurement; blindly enlarging
      max_model_len only accommodates whatever the largest known case is
      and could still be exceeded by an image not yet encountered.

      Picked a shared ~1280-image-tokens-per-image budget (matches a
      commonly-used Qwen-VL example default, not an arbitrary number),
      converted to each model's own max_pixels via its patch/merge
      geometry (Huatuo: 14px patch x 2x merge = 784 pixels/token, so
      max_pixels=1280*784=1,003,520; Qwen3-VL: 16px patch x 2x merge =
      1024 pixels/token, so max_pixels=1280*1024=1,310,720).

      Re-ran measure_prompt_lengths.py with the cap applied (real
      measurement again, not a formula estimate) to confirm it actually
      works: new max for BOTH models dropped to 7,628 tokens (same value
      for both -- expected, since the cap targets the same per-image
      token budget for both). p95/p99 also dropped substantially (Qwen:
      1393/1625; Huatuo: 1405/1820).

        dataset_mm/generated_traces/Qwen3-VL-8B-Instruct/{vqa_rad,slake,medxpertqa_mm}/
      (47 files each, counts verified after every move.)

      Despite Huatuo needing ~30% more prompt/vision tokens per image
      than Qwen (see part e above), Huatuo finished in under half
      Qwen's wall-clock time. Measured per-question throughput (same
      batches, excluding any pre-existing/resumed batches from the
      timing) showed Huatuo ~2.5-3x faster across every data source
      (e.g. vqa_rad: Huatuo 2.6s/q vs Qwen 6.3s/q; medxpertqa_mm:
      Huatuo 7.1s/q vs Qwen 23.1s/q). Root cause, confirmed by
      measuring actual generated-text length (not assumed): on the
      same vqa_rad batch, Huatuo's solutions average 583 chars
      (median 618, max 2,205) vs Qwen's 1,123 chars (median 1,088,
      max 18,152). Qwen generates roughly 2x more text per response on
      average, plus a much fatter tail of very long outputs. Since
      vllm decode time scales with tokens actually generated (not
      prompt length, which is parallelized during prefill), Qwen's
      more verbose reasoning -- and occasional runaway generations --
      cost far more wall-clock time per question than Huatuo's terser
      responses, outweighing Huatuo's higher per-image token cost.

      Investigated one specific Qwen failure mode found while
      checking scoring completeness: in
      mm_benchmark_medxpertqa_mm_Qwen3-VL-8B-Instruct_64_batch0.json,
      all 16,000 solutions (250 q x 64 samples) have a `score` field
      (none missing, none unscored -- this file is all-MC so "None"
      scores don't apply), but 217/16,000 (~1.4%) have `answer: None`
      -- the generated text got stuck in a repetition loop and never
      reached a parseable final-answer line, running to the
      max_tokens=4096 cap; these are auto-scored 0 (counted as
      incorrect), not left unscored. Confirmed this is NOT a
      regression: smoke test 5 used the identical temperature=0.7 /
      top_p=0.9 / max_tokens=4096 config (no repetition_penalty set in
      either case -- vllm default of 1.0, i.e. none), and its typical
      output length matches the full run almost exactly (mean 1,066
      vs 1,123 chars on vqa_rad) -- only the full run's much larger
      sample count (16,000 vs 16 generations checked) was large enough
      to surface this ~1-1.5% low-probability decoding tail; at 16
      samples the odds of seeing zero such cases by chance are ~80%.
      Not fixed (would need a `repetition_penalty` added to
      SamplingParams in python_mm/3_generate_traces.py:336) -- left as
      a known, quantified, low-rate artifact rather than re-running
      the full generation.
